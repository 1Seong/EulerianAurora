# 맵 생성 재구축

신규 맵에 일반 길·비인접 포탈·대시·레이저·고스트·인버터를 배치한다. 검증된 후보를 인게임 미리보기·이전 후보·적용 UI에 전달한다.

## 입력과 계획

- `GenerationUiSettings`: 기믹 자동 여부·수동 사용 마스크, 난이도 자동 여부·수동 난이도만 관리한다. 개수나 필수 순서 필드는 없다. 자동일 때 보관된 수동 값은 검사와 적용에서 모두 제외한다.
- `GenerationConditions`: 백엔드에서 자연어를 해석하여 전달한 구조화된 조건이다. 허용 기믹, 난이도, 구체적 개수, 필수 기믹과 작동 순서를 담을 수 있다. 게임에는 자연어 파서가 없다. 백엔드 API 연결은 아직 미구현이다.
- `GenerationConditionResolver`: UI 제한과 추출 조건을 병합한다. 명시적 난이도 충돌, 금지 기믹 배치/필수 사용, 필수 기믹 0개, 잘못된 값, 예산 초과를 거절한다. 충돌을 임의로 덮어쓰지 않는다.
- `GenerationPlan`: 실제 선택된 난이도, 난이도가 자동 추첨되었는지, 유효 허용 범위, 필수 기믹/순서, 개수, 예산과 예약액을 불변 스냅샷으로 보관한다. `MapGenerationResult.Plan`으로 반환한다.

UI 기믹 자동은 자연어 조건을 해제하지 않는다. 자동에 자연어 조건도 없으면 모든 종류를 선택 후보로 허용한다. 수동 「사용 기믹」에서 선택한 종류는 각각 최소 한 번 생성된 정답 시퀀스에서 실제로 사용해야 하며, 선택하지 않은 종류는 제외한다. 모두 해제하면 일반 길만 생성한다. 기존 `AllowedGimmicks` 필드명은 호환을 위해 유지하지만, 수동 UI 값은 허용 범위와 필수 사용 목록 모두에 반영한다. 자동에서는 보관된 수동 선택을 적용하지 않는다. 선택 기믹과 백엔드의 0개/금지 조건은 충돌로 처리하며, 필수 사용은 모든 가능한 정답에서 사용을 강제한다는 의미는 아니다.

UI 난이도가 자동이고 자연어에 난이도가 있으면 그 난이도를 적용한다. 둘 다 미지정이면 최소 배치 비용을 감당하는 난이도 중 요청 seed로 추첨한다. 같은 seed/조건은 같은 결과를 낸다. 명시된 쉬움이 예산 부족이면 몰래 어려움으로 올리지 않고 실패를 알린다. 자동 난이도는 더 이상 보통으로 고정되지 않는다.

## 예산

| 종류 | 비용 | 쉬움 가중치 | 보통 가중치 | 어려움 가중치 |
|---|---:|---:|---:|---:|
| 일반 길 | 1 | 12 | 12 | 12 |
| 대시 | 2 | 5 | 5 | 5 |
| 포탈 쌍 | 3 | 5 | 5 | 5 |
| 레이저 | 4 | 3 | 3 | 3 |
| 고스트 | 5 | 1 | 3 | 6 |
| 회전 레이어 | 8 | 1 | 3 | 6 |
| 인버터 | 10 | 1 | 3 | 6 |

최대 풀은 쉬움 24 / 보통 45 / 어려움 80이다. 모두 조정용 초기값이며 실제 플레이 난이도를 보장하지 않는다. 솔버 탐색 상태 한도와도 별개다.

필수 기믹과 명시적 배치 개수의 비용을 먼저 예약한다. 공통 조건 해석기는 생성 전략의 예약 비용 추정기를 받을 수 있다. 반복 순서의 작동마다 별도 기믹 칸을 예약하며, 포탈 뒤 이동과 대시·고스트의 착지에 필요한 일반 길 비용도 포함한다.

## UI

- 기믹 자동/난이도 자동은 독립적이며 기본값은 자동이다. 개별 선택은 흐리게 비활성화하고 자동 해제 시 이전 값을 유지한다.
- 난이도는 쉬움/보통/어려움 중 하나만 선택한다. 기믹 개수 UI는 없다.
- 텍스트 없이 UI 설정만으로 요청할 수 있다. 백엔드 연결 전에는 텍스트 요청을 처리할 수 없다고 안내한다. 추후 백엔드 응답을 받으면 그 구조화된 조건과 로컬 UI 설정의 충돌을 검사한다.
- 보조 창은 1440×900 기준 우측에 340×460 크기로 배치한다. 상단 바 드래그로 이동할 수 있고 화면 경계에서 제한한다.
- 전체 화면 입력 차단용 배경은 완전히 투명하다. 맵을 어둡게 하거나 흐리게 하지 않는다.
- 다른 Canvas의 UI 오브젝트를 SetActive(false)로 숨기고 닫을 때 원래 activeSelf로 복원한다. 에디터와 보조 창이 들어 있는 공통 조상은 끄지 않고 UI 형제 가지를 숨긴다. 버튼 interactable 값은 변경하지 않는다.
- 긴 안내는 패널 내부에서 스크롤하여 버튼과 겹치지 않게 한다.

## 신규 맵 생성 흐름

1. CreateMap만 허용한다. 현재 맵은 기본 크기를 읽을 때만 사용하고 원본 타일은 변경하지 않는다. 보존 조건, 이동/수정 작업은 명시적으로 미지원 처리한다.
2. 수동 UI에서 선택한 종류는 필수다. 회전을 선택하면 미지원 안내를 반환한다. 자동에서는 지원되는 기믹을 예산에 맞춰 선택한다.
3. 무작위 표면 시작점에서, 현재 시뮬레이션 위치와 타일 상태를 바탕으로 다음 배치와 이동을 제안한다.
4. 일반 이동은 빈 이웃 칸에 길과 입력 하나를 추가한다. 포탈 동작은 입구, 비인접 출구, 출구 이후 길을 배치하고 입력 두 개를 추가한다. 포탈 출구에서 이어갈 수 있는 것을 초기 지원 범위의 구성 조건으로 삼는다.
5. 바뀐 초기 배치에서 입력 전체를 PuzzleSolver.Simulation으로 다시 재생한다. 이 경계는 솔버 Search.Advance를 그대로 호출한다. 이동/순간이동/색칠 규칙의 복제 구현은 없다. 입력과 실행 결과 위치·기믹 이벤트는 구분한다.
6. 실패하면 배치, 포탈 연결, 입력, 소비 비용을 함께 되돌린다. 필수 포탈과 명시적 개수의 예약 비용을 일반 길이 소진하지 못하게 한다. 시작점은 비용을 부과하지 않는다.
7. 완성 후보는 PuzzleSolver.VerifySequence로 처음부터 다시 재생하여 클리어와 필수 기믹 사용을 확인한다. 이후 독립된 MapDocument와 Witness를 만들어 UI에 전달한다. 생성 시 별도 Solve 탐색을 또 돌릴 필요는 없다.

포탈·대시·레이저 작동 순서의 반복은 서로 다른 기믹 칸을 사용하여 지원한다. 명시한 기믹 개수보다 더 많은 반복 사용은 현 단계 미지원이다. 필수 기믹/순서는 제공한 해답에서 확인한다. 모든 해답에서의 강제성, 우회 방지, 유일해는 검사하지 않는다.

예산은 최대치다. 실제 목표 비용은 최대 풀의 약 50~100%에서 고르고, 작은 보드의 일반 길 목표는 가용 표면의 약 75%로 제한한다. 필수 배치는 먼저 확보한다. 난이도는 아직 체감 난이도 측정값이 아니라 생성 분량 설정이다.

## 대시 생성

대시 칸과 해당 방향의 빈 착지 칸을 함께 배치한다. 6방향 중 실제로 이동할 수 있는 방향을 고른다. 입력은 대시 진입용 하나만 기록하고, 강제 이동은 기존 솔버 전이가 실행한다. 대시를 배치했다는 사실만으로 성공 처리하지 않고 실제 강제 이동 이벤트와 최종 클리어를 확인한다.

현재는 대시 이후 일반 길에 착지하는 기본형이다. 연속 대시 및 대시에서 바로 포탈로 진입하는 배치는 아직 생성하지 않는다. 포탈 구간과 대시 구간을 한 맵에서 조합하는 것은 지원한다.

`RequiredOrder`는 `DashUsed`와 `PortalExit`를 조합할 수 있다. 예: `DashUsed → PortalExit → DashUsed`. 기믹별 필수 개수·예약 비용과 순서 진행 상태를 함께 관리하고, 되돌릴 때 모두 복원한다. 뒤 순서에 필요한 기믹을 앞에서 소진하는 후보는 생성하지 않는다. UI에는 개수 설정을 추가하지 않았으며, 대시 사용 선택과 자동 설정만 그대로 사용한다.
## 레이저 생성

레이저 칸, 발사 방향의 일반 길 1~3칸, 발사 후 이동할 별도 일반 길을 함께 배치한다. 입력은 진입 → 발사 → 이동 순서다. 발사 입력에서는 플레이어가 움직이지 않으며, 실제 색칠과 사거리 판정은 기존 솔버의 FireLaser 규칙을 사용한다. 발사 여부는 LaserFired 이벤트로 확인한다.

레이저 비용 4에 발사 대상 길과 이동할 길의 비용을 더한다. 이 최소 비용은 GenerationPlan의 예약액과 자동 난이도 선택에도 반영한다. 필수 레이저 하나에는 최소 6을 예약하고, 더 긴 발사 구간은 추가 비용을 지불한다. 후보 실패 시 대상 길·레이저·이동 길·입력·예산·순서 진행 상태를 함께 되돌린다.

나중에 추가한 길이 앞선 레이저의 사거리를 바꿀 수 있으므로 모든 배치 후보에서 처음부터 입력을 재생한다. 레이저가 칠한 칸으로 이동하는 입력은 그 칸이 다시 열렸을 때 통과한다. 후속 인버터를 발사 대상으로 삼는 경우는 아래에 설명한다.

포탈·대시와의 혼합 순서 및 반복 발사를 지원한다. 같은 레이저를 재사용하는 대신 여러 레이저 칸을 배치한다. 모든 해답에서 발사가 강제되는지에 대한 우회 검사는 여전히 별도 미구현이다.
## 고스트 생성

고스트 칸에 진입한 뒤 `TileHelper.GhostCount`(현재 5)번 이동한다. 앞의 네 번은 이미 칠한 기존 칸을 되짚고, 마지막 이동에서 새 일반 길을 칠하면서 효과를 끝낸다. 같은 칸의 반복 방문을 허용하므로 일반 해밀턴 경로를 확장하는 방식이 아니다. 기존 기믹 칸도 이미 칠해져 있다면 통과할 수 있으며, 실제 이동과 기믹 사용 제한은 솔버의 공통 전이를 따른다.

고스트 칸 5 + 새 착지 길 1의 비용을 예약한다. 입구마다 깊이 `GhostCount`의 이동 탐색을 최대 128회 수행하여 후보를 최대 8개만 확보한다. 모든 기존 칸이 칠해진 상태에서 이 배치를 제안하고, 처음부터 입력을 재생하여 마지막 이동에서 고스트 효과가 끝나는지 확인한다.

`GhostUsed`는 효과를 얻은 뒤 첫 이동에서 한 번 기록한다. 다섯 번 이동했다고 다섯 개의 필수 고스트 사용을 만족시키지 않는다. 포탈·대시·레이저와의 필수 순서 및 여러 고스트의 반복 사용을 지원한다. UI의 고스트 사용 선택과 자동 설정을 적용한다.

현재 생성 전략은 **칠해진 구간을 되짚고 새 일반 길에 착지하는 기본형**이다. 아직 칠하지 않은 기믹을 효과 중 통과하거나, 효과 종료와 동시에 다른 기믹을 발동시키는 복합 구간은 생성하지 않는다. 정답 재생은 검증하지만 모든 해답에서 고스트 사용이 필수인지에 대한 우회 검사는 아직 하지 않는다.

## 인버터 생성

인버터에 진입한 뒤 열린 기존 칸을 시뮬레이션에서 읽고, 각 분기의 이동을 공통 전이 규칙으로 검증한다. 열린 구간에는 방문했던 칸과 레이저로만 칠한 칸이 함께 들어간다. 홀수 번째 반전 이후 새 빈자리에 추가할 칸은 처음부터 재생했을 때 닫히므로, 이 구간에서는 이미 열린 칸을 탐색한다.

레이저 대상 길을 후속 인버터로 바꾸는 후보도 시험한다. 초기 보드에서 해당 타일을 교체하고 앞선 발사부터 재생한 뒤, 이전 이벤트 순서를 보존하면서 새 입력에서 인버터가 발동했는지 확인한다. 인버터 비용은 10이며, 발사 대상 길을 교체하면 기존 길 비용 1을 빼고 계산한다. `InverterActivated` 순서와 명시 개수는 생성된 보드와 클리어 입력으로 검증한다.

포탈과 함께 배치할 때는 비인접 출구 후보 중 시작점에 닿는 위치도 시도한다. 반전 뒤 출구 쪽에서 입구 쪽 경로로 돌아올 수 있는지 실제 재생으로 확인한다.

## 실행 한도와 실패

기본 MapGenerationLimits는 배치와 반전 후 이동을 합쳐 1,500회, 시작점 시도 최대 8회, 생성 시간 2,500ms다. 각 시작점에 남은 시도 예산을 분배한다. 시간 한도는 협력적 검사로 적용하므로 진행 중인 단일 연산 시간만큼 초과할 수 있다. 닫기/취소 토큰은 후보 재생 중에도 확인한다.

- CandidateFound: 클리어 입력 재생을 통과한 후보.
- UnsupportedConditions: 미지원 수정/기믹, 조건 충돌 등.
- NoCandidateFound: 이번 구성 방식과 시도에서 후보를 찾지 못함. 일반적인 불가능 증명이 아니다.
- SearchLimitReached: 시간/배치 시도 한도로 중단. 기존 UI 후보는 유지한다.
- 취소: OperationCanceledException을 UI에서 처리한다.

같은 시드와 조건은 한도에 걸리지 않을 경우 같은 후보를 재현한다. 이전에 나온 후보도 다시 허용한다. 후보는 소비 비용·배치 시도·되돌림 횟수를 기록한다.

## 자연어 처리 경계

자연어 입력 → 백엔드 AI 해석 → 구조화된 MapAssistRequest 응답 → 로컬 UI 설정과 충돌 검사 → 생성·솔버 검증 순서다. 게임 내부의 정규식 파서와 입력창 JSON 해석은 제거했다. 데이터 계약은 MapAssistContracts.cs에 유지한다. MapTools.Generate는 이미 구조화된 요청을 받는 진입점이며 원문 텍스트를 해석하지 않는다. UiConditions는 로컬 전용이고 JsonIgnore로 백엔드 응답에서 분리한다. 실제 HTTP 호출, 응답 역직렬화와 오류 처리, 백엔드 API 스키마 확정은 이후 연결 단계에서 구현한다.
